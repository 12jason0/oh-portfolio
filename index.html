01 · 인증 설계01 · Auth designJWT · token_version

로그아웃한 토큰이 다시 사용되지 않도록Making sure a logged-out token can't be used again

문제Problem

로그인 토큰(JWT)을 localStorage에 저장해서 JavaScript로 읽을 수 있었습니다. 로그아웃해도 토큰은 1년 만료 전까지 그대로 유효했습니다.The JWT sat in localStorage where JavaScript could read it, and it stayed valid for its full year even after logout.

해결Solution

HttpOnly 쿠키 + 서버의 token_version 검증HttpOnly cookie + a server-side token_version check

토큰을 HttpOnly 쿠키로 옮겨 JavaScript가 직접 읽지 못하게 했습니다. 로그아웃하거나 비밀번호를 바꾸면 버전을 올려 이전 토큰을 거부합니다.The token moved into an HttpOnly cookie so JavaScript can't read it, and logout or a password change bumps the version so older tokens are rejected.

결과Result

배포 후, 한 기기에서 로그아웃하면 다른 기기의 이전 토큰이 거부되는 것을 확인After deploy: logging out on one device rejects the old token on another

판단 근거 · 대가 · 운영 확인 보기Reasoning · trade-offs · production check

왜 쿠키인가Why a cookie

localStorage·sessionStorage·HttpOnly 쿠키를 비교했습니다. 앞의 둘은 JavaScript로 읽을 수 있어서 HttpOnly 쿠키를 골랐습니다.I compared localStorage, sessionStorage and an HttpOnly cookie. The first two are readable from JavaScript, so I chose the cookie.

왜 기간을 줄이지 않았나Why not a shorter lifetime

토큰 기간을 줄이면 앱에서 자주 다시 로그인해야 합니다. 그래서 1년 자동 로그인은 두고, 서버에서 끊을 수 있게 만들었습니다.A shorter lifetime would force frequent re-login in the app, so I kept the one-year login and made it revocable on the server.

구현Build

로그인 7곳에 흩어진 토큰 발급 코드를 함수 하나로 합쳤습니다. 버전 값이 없는 기존 토큰은 0으로 처리해 전환할 때 기존 사용자가 튕기지 않게 했습니다.Merged token issuing from 7 login paths into one function. Tokens without a version count as 0, so existing users stayed signed in through the switch.

감수한 것Trade-offs

인증 확인마다 DB 조회가 한 번 늘고, 한 기기에서 로그아웃하면 모든 기기에서 함께 로그아웃됩니다. 쿠키는 요청에 자동으로 실리기 때문에 SameSite=Lax로 다른 사이트에서 보낸 요청에는 실리지 않게 했습니다.One extra DB lookup per check, and logging out signs you out everywhere. Cookies ride along automatically, so SameSite=Lax keeps them off requests sent from other sites.

운영에서 확인In production

배포 후 응답 헤더로 미들웨어가 운영 환경에서 실행되지 않는 문제를 찾아 런타임 설정을 되돌렸습니다. 그다음 한 기기에서 로그아웃했을 때 다른 기기의 이전 토큰이 거부되는지 확인했습니다.After deploy, response headers showed the middleware was not running in production, so I restored the runtime setting. Then I confirmed that logging out on one device rejects the old token on another.

적용 범위Scope

토큰을 JavaScript로 직접 읽는 것과 로그아웃 이후 사용을 막은 것입니다. 모든 XSS·CSRF를 해결했다는 뜻은 아닙니다.This stops JavaScript from reading the token and stops use after logout. It does not mean every XSS or CSRF risk is solved.

res.cookies.set("auth", token, {

  secure: process.env.NODE_ENV === "production",
  sameSite: "lax",
  path: "/",
  maxAge: serverConfig.authTokenMaxAgeSec,

인증 문제로 보이던 결제 오류의 원인 찾기Finding the real cause of a checkout error that looked like auth

문제Problem

QuoteCrate 앱 안에서 결제 요청이 401로 실패했습니다. 처음에는 인증 토큰 문제라고 보고, 이틀 동안 그 가설로 원인을 찾았습니다.Inside QuoteCrate, the checkout request failed with 401. I assumed the auth token was at fault and spent two days on that theory.

해결Solution

성공·실패 요청을 나란히 비교해 가설 수정Compared good and failing requests side by side and changed the theory

iframe 안에서 외부 결제 화면으로 이동하는 과정이 막힌 것이 원인이었습니다. Shopify App Bridge로 상위 창에서 이동하도록 바꿨습니다.The redirect to the external checkout was being blocked inside the iframe. I moved it to the top window with Shopify App Bridge.

결과Result

결제 흐름을 복구하고 Shopify App Store에 출시Checkout restored, and the app shipped on the Shopify App Store

원인 추적 과정 보기How I traced it

처음 가설First theory

401이라는 코드만 보고 인증 토큰이 잘못됐다고 판단했습니다.The 401 code alone made me assume the auth token was wrong.

가설을 바꾼 근거What changed my mind

성공한 요청과 실패한 요청을 직접 비교하면서, 인증이 아니라 iframe 안에서 외부 결제 화면으로 넘어가는 이동이 막힌다는 걸 확인했습니다.Comparing a good request with a failing one showed it was not auth: the move to the external checkout was blocked inside the iframe.

지금 일하는 방식What I do now

왜 만들었나Why

생리 주기는 기록하는 사람만 알고, 연인은 언제 무엇을 해주면 좋을지 모르는 경우가 많습니다. 기록하는 사람이 적으면 파트너가 같은 달력을 보고, 필요한 배려를 버튼 하나로 주고받게 만들었습니다.Usually only the person tracking knows the cycle, and the partner doesn't know when or how to help. Here the tracker logs, the partner sees the same calendar, and care is requested and answered with one tap.

주요 기능Features

  • 주기 기록·예측: 시작/종료, 통증·기분, 다음 생리일·가임기·배란일 예측Cycle log & prediction: start/end, pain & mood, next period, fertile window, ovulation
  • 파트너 연결: 8자리 코드(15분, 1회용), 잠시 멈추기, 연결 끊기Partner link: 8-character code (15 min, single use), pause, unlink
  • 배려 요청: 칩 한 번으로 요청 → 파트너 답장(봤어요 / 도와줄게요 / 했어요)Care requests: one-tap chips → partner replies (seen / on it / done)
  • 푸시 알림: 배려 요청·답장·예정일 (웹 푸시 + 매일 예약 작업)Push: requests, replies and upcoming dates (web push + daily scheduled job)
  • 리포트: 평균 주기·기간·예측 오차, 주기 차트, 지난 기록 표Reports: average cycle and length, prediction error, cycle chart, history table
  • 파트너 커뮤니티: 게시판, 댓글·답글, 신고 3회 자동 숨김, 차단, 운영자 신고 관리Partner community: board, comments & replies, auto-hide after 3 reports, blocking, admin report review
  • 계정: 이메일·카카오 로그인, 비밀번호 변경, 회원 탈퇴Accounts: email & Kakao login, password change, account deletion

기술적으로 신경 쓴 부분Engineering decisions

  • 개인 맞춤 예측: 최근 6개 주기 가중 평균, 튀는 주기 자동 제외, 기록이 적을 때는 평소 주기와 섞어 쓰고 ±범위 표시, 과거 기록으로 예측 오차 계산Personal prediction: weighted average of the last 6 cycles, outliers dropped, blended with the usual cycle when data is thin, ± range shown, error measured against past records
  • 건강 정보 보호: 파트너에게는 결과 날짜만 전송, 요청마다 서버에서 공유 권한 재확인, 잠금화면 알림에 건강 단어 제외Health data: partner gets dates only, sharing rights rechecked server-side per request, no health words on lock-screen notifications
  • 보안: scrypt 비밀번호 해시, 세션·초대 코드 해시 저장, 로그인·가입·코드 입력 횟수 제한, 탈퇴 시 데이터 삭제 + 카카오 연결 해제Security: scrypt hashing, hashed sessions and invite codes, rate limits on login, signup and code entry, data deletion plus Kakao unlink on account removal
  • 동시성: 연결·끊기·탈퇴가 동시에 일어나도 꼬이지 않게 트랜잭션과 잠금 순서를 설계Concurrency: transactions and lock ordering so link, unlink and deletion can't collide
  • 성능: 서버와 DB를 같은 지역(싱가포르)에 두고, 서비스 워커 캐시로 재방문 때 받는 파일을 20개 → 4개로 줄임Performance: server and DB in the same region (Singapore); service-worker cache cuts files fetched on a revisit from 20 to 4
  • 법적 준비: 개인정보처리방침, 민감정보·국외 이전 동의 분리, 만 14세 확인Legal: privacy policy, separate consent for sensitive data and overseas transfer, age-14 check
  • 테스트: 자동 테스트 235개 (Vitest)Tests: 235 automated tests (Vitest)
